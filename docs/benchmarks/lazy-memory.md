# Lazy partition memory and decode benchmark

Synthetic data only. Production behavior is unchanged in the measurement step.

## Reproduce

From the repository root, choose a new filesystem-backed artifact directory:

```sh
./scripts/profile-lazy-memory.sh check /var/tmp/proseql-memory-evidence
./scripts/profile-lazy-memory.sh build /var/tmp/proseql-memory-evidence
./scripts/profile-lazy-memory.sh before /var/tmp/proseql-memory-evidence
./scripts/profile-lazy-memory.sh summarize /var/tmp/proseql-memory-evidence
./scripts/profile-lazy-memory.sh feedback /var/tmp/proseql-memory-evidence
```

These are local Nix-shebang scripts. `build` uses the project's pinned development toolchain. `check` runs only focused tests, cargo check, clippy and formatting, not full suites. `before` runs each mode with the default optimized binary, checkpoint-only binary and DHAT binary, then runs the existing `timeseries_bench` as a separate control. Existing artifacts are not deleted. Do not reuse `before` on an evidence directory you want to preserve: its log paths would be overwritten. Data creation uses `create_new` and refuses incompatible or incomplete fixture reuse.

`feedback` is deliberately red on an over-budget baseline. It generates 10×1,000 rows and 100 eager IDs in a separate directory and uses DHAT live/high-water allocated bytes. It exits nonzero above 1024 resident bytes/row or open heap + two target-sized partitions +50 MiB transient heap. The limits are unit-tested independently. Use the full 43k fixture for final RSS/transient acceptance; the small feedback command cannot prove that guarantee.

Direct benchmark options:

```sh
# Run preparation in its own process, never in the measured process.
cargo run --manifest-path crates/Cargo.toml -p proseql-native --profile memory-profile \
  --example lazy_memory_bench -- --data-dir /var/tmp/proseql-memory-data --prepare-only
cargo run --manifest-path crates/Cargo.toml -p proseql-native --profile memory-profile \
  --example lazy_memory_bench -- --data-dir /var/tmp/proseql-memory-data --mode zero
```

| Option | Default / meaning |
|---|---|
| `--data-dir PATH` | `/var/tmp/proseql-lazy-memory-v1`; generated bytes and completion marker |
| `--rows-per-month N` | 43000; positive, at most 1000000 |
| `--id-rows N` | 10000; positive, at most 139420 |
| `--prepare-only` | Create deterministic fixture, then exit |
| `--mode zero` | Ascending ten one-month queries, keeping zero rows |
| `--mode ascending` | Ascending scopes of 1,2,3,1,2,3,1,2,2,1 months; return all matching rows sorted by timestamp |
| `--mode scan` | One ten-month ordered query scope, keeping zero rows |
| `--mode eager-id` | Open small eager ID-only collection, with no timestamp index |
| `--heap-profile PATH` | DHAT output; requires `--features heap-profile` |
| `--check` | Enable allocated-byte failure thresholds; requires `--heap-profile` |

## Method and limits

The v1 fixture has exactly 430,000 rows, 12 flat fields, 316 bytes including each newline, and 135,880,000 bytes across January–October 2025. IDs, metric names and values are generated. Each month's timestamps cover that calendar month in UTC. No consumer directory is read. The eager file contains only synthetic IDs.

Every measured mode opens a new `NativeRuntime` against actual JSONL files. Monthly sources use `TimeBucket::Month`, `append_only`, `DuplicateIdPolicy::IgnoreIdentical`, an ordered `timestamp` index and lazy max=1. The timed call is `NativeRuntime::query`, not the extra explain work of `query_with_stats`. Counts and final cache residency are checked after each query. This checks current behavior, not the future transient guarantee. `ascending` intentionally includes result cloning; `zero` and `scan` retain no output rows and isolate native loading/query/eviction from consumer DTO work. Page cache is warm. The host is shared; wall time is not a controlled CPU microbenchmark.

`memory-profile` inherits release optimization and adds line symbols. Three independently built executables separate default timing, callback-only overhead and DHAT overhead. `LM_QUERY` and `LM_SUMMARY` are JSON-line output. `LM_PHASE` on stderr records begin/end checkpoints. Heap fields are null in binaries without an active DHAT profile. RSS uses Linux `/proc/self/status`; GNU time records peak RSS and whole-process wall time independently.

Phase boundaries are inclusive and nested. Do not sum them. Read includes filesystem recovery. ID validation includes decode, cached text access, checking and temporary-value destruction. Schema decode/map construction includes destroying its input values. Native resident validation, record insertion and index maintenance share one boundary. Query includes its planner; eviction includes removal/index work. Remaining uninstrumented gaps include snapshot copying, bucket checks and drop work. Do not assign these gaps to a named phase by subtraction.

Heap high-water and RSS high-water are cumulative at each checkpoint, not phase-local maxima. Live-byte deltas are not ownership attribution. DHAT stacks provide sites and `gb` bytes live at global peak, `eb` bytes live at profile end, total allocation bytes/counts and summed lifetimes. The profiler stops before runtime close while resident data is alive. End-live lifetimes are right-censored. DHAT metadata and allocator retention are not tracked as application bytes, so profiled RSS is not directly comparable to default RSS. Diagnostic callback allocations are tracked and visible as their own sites.

### Scope interpretation

`width` and the legacy `partition_scope` output field mean **requested timestamp months**, not actual partition reads. The current string-based conservative pruner includes the next bucket for an exclusive `.000Z` boundary. The checkpoint trace shows that the first `zero` query loads two files, eight subsequent queries load one each, and October is already resident for the final query. A requested 3-month window can load four files. This is preserved baseline behavior. Do not call the last warm query a one-month cold-load result. Tightening pruning requires proving lexical comparison parity for valid timestamps with different fractional precision, not assuming normalized chronological ordering.

Heap-derived resident fields from unprofiled logs are zero placeholders in the measured `941978d` harness and are not measurements. The evidence follow-up changes these fields to null, renames `partition_scope` to `requested_months`, and applies explicit check budgets to the actual resident row count; it does not change the profiled query paths or production behavior. Use only DHAT live-byte fields for allocation claims. GNU time's maximum RSS includes profiler shutdown; phase/status RSS checkpoints can be smaller.

|---|---|---|

The System meter and DHAT run in **separate processes**. Wrapping DHAT would
also count its deliberately untracked profiler metadata. The meter uses fixed,
nonallocating phase state and serial accounting. Nested phases include child
work. Observer JSON/output is paused and excluded from phase attribution. Its
`allocated_requested` counts full successful realloc destination requests;
DHAT uses a different cumulative convention. Do not compare those totals as
identical quantities. A real System-allocator unit test exercises allocation,
zeroing, growth, free and nested peaks.

`max_endpoint_excess_bytes` is the largest per-span peak minus that span's
larger endpoint. It is not an ownership attribution. RSS observations remain
begin/end samples and a cumulative process high-water mark in these original
four roles. **Correction: this kernel supports resetting its own VmHWM. The
separate RSS-only process below now measures actual phase-local RSS peaks.**
The original checkpoint/DHAT values are not relabelled as local peaks. A separate
end-of-scan `mallinfo2`/`malloc_trim` diagnostic explains allocator-held space;
it does not improve primary timings or acceptance RSS numbers.

The literal RSS acceptance formula is evaluated separately for zero results,
one full ten-month zero-result scan, and all-match ascending 1–3-month output.
It has **no output allowance**. A cache bound does not make a formula failure
pass: matching-row buffers, exact ID workspace, pins, watch values and allocator
retention still consume process memory. Output explains an all-match miss; it
does not remove the miss from the target table.

The native 64-bit layout probe measures a 1651-byte canonical payload for one
fixture row, before engine/source/index metadata. Each `(String, Value)` pair
occupies 96 bytes; 12 pairs alone need 1152 bytes. This is a floor for the
**retained public canonical representation**, not proof that every engine
design must exceed 1024 B/row. A compact structured/columnar store with borrowed
record views could reduce that cost. It would need a new borrowed-view and
materialization contract, compatibility work for existing `&Value` access,
and query/mutation/watch parity tests. That redesign is not implemented here;
opaque blobs and disabling insertion ordering are not substitutes.

For supplemental local BEFORE peaks, a source archive is pinned to captured
`941978d0fb22f5b0b66b7ef40d8e6fb6d00584bb`, outside every worktree. Its manifest
verifies 124 original crates files unchanged; only the benchmark checkpoint
function, benchmark Cargo feature and new System meter differ. Eleven fixture
hashes match BEFORE. Original BEFORE logs/profiles are not overwritten. This
counter-only run supplies missing local allocation peaks, not replacement
production timings.

### RSS observer caveats

- Kernel RSS/HWM accounting is approximate and can be batched. Values are kernel counters, not ownership or allocator attribution.
- Observer status reads, resets, mutex/stack, code pages and stderr formatting contribute overhead. Direct formatting avoids per-event serde Value trees.
- Peaks are inclusive of nested and any concurrent process-thread work. Benchmark watch threads are disabled; cross-thread span nesting is rejected.
- Sampling current RSS together with HWM uses the larger value to tolerate accounting snapshots. Reset intervals are joined by maxima, not added.
- Wall times here include observation overhead and shared-host scheduling; original unprofiled acceptance results remain unchanged.

### Permanent RSS-only reproducer and regression proof

```sh
./scripts/profile-lazy-memory.sh build ARTIFACT_DIR
./scripts/profile-lazy-memory.sh rss ARTIFACT_DIR
```

`build` makes a separate `bin/rss` executable with `--features phase-rss`.
`rss` reads the same v1 fixtures and writes only `phase-rss/` diagnostic logs.
It refuses to overwrite its evidence directory. The default `after` timing,
DHAT and allocation-meter roles do not reset their HWM. When profiler features
are combined, heap/allocation profilers take precedence and disable the RSS
reset observer. Normal default benchmark HWM fields stay unchanged; in the
RSS-only role, acceptance HWM fields are null rather than misleading reset
values. Do not use GNU time's maximum from this observer process as the
unprofiled process acceptance peak.

The observer uses fixed stack/buffer state, reads `/proc/self/status`, then
writes only `5\n` to its own `/proc/self/clear_refs`. It samples the old HWM
**before** clearing it, propagates the maximum to **all** active parents, and
pushes/pops nested spans. It rejects cross-thread span nesting and malformed
span exits. Output uses direct formatting instead of allocating serde trees.
Observer code pages, stack, mutex, proc I/O and logging remain overhead; kernel
RSS/HWM counters use approximate/batched accounting. This measures inclusive
process RSS during a span, not bytes owned exclusively by that phase.
